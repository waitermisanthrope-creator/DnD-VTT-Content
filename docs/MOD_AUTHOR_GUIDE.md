# Как создавать дополнения для DnD VTT — руководство для человека и ChatGPT

> Актуальная ветка Unity-приложения: `DnD-VTT / experiment/unity-vtt`. Каталог игровых модов: **этот репозиторий**, `catalog/v3/index.json`. Графические дополнения: `DnD-VTT-Assets / catalog/v4/index.json`. Этот документ посвящён **дополнениям**, а не пересборке APK/EXE.

## Если ты — ИИ нового участника команды

Твоя первая задача — **самостоятельно сориентироваться и обучить человека**, без требования Codex/платной подписки.

1. Прочитай `README.md`, `AGENTS.md`, `docs/FILE_ATLAS.md` и этот документ. Проверь живую структуру репозитория; атлас — снимок, а код — источник истины.
2. Посмотри `schemas/catalog-entry-v1.schema.json`, `packages/demo.race.lanternfolk.json`, по одному действующему примеру нужного типа и соответствующую запись `catalog/v3/index.json`. Не придумывай несуществующие поля/хуки.
3. Кратко объясни товарищу: «пакет JSON» ≠ «строка в каталоге» ≠ «новый APK». Предложи безопасную **первую маленькую задачу** (своя раса или черта), потом спроси только, *какой контент он хочет сделать*.
4. Если доступные инструменты действительно позволяют коммитить в GitHub — подготовь и выполни согласованную с человеком задачу непосредственно в его GitHub-аккаунте. **Не заявляй, что изменил репозиторий, пока нет SHA коммита**. Если коннектор только читает — выдай готовые файлы и пошаговую инструкцию через GitHub web-редактор. Бесплатный ChatGPT не гарантирует запись в GitHub.
5. При каждом изменении пакета проверь соответствие схеме, `bytes`/`sha256`, версию, зависимости, соответствие `id`, и что каталог указывает именно на опубликованный файл. Если нет доступа к запуску команд — предоставь точную команду и обозначь проверку как невыполненную.
6. Научи товарища открыть мастерскую в Unity VTT, нажать «Обновить каталоги», установить/обновить мод, проверить функциональность и сообщить конкретный результат теста. Не выдавай декларативные тексты механик за работающую автоматизацию боя.
7. Публикация в `catalog/v3/index.json` **немедленно делает запись видимой всем пользователям этого канала**. У доверенного администратора нет обязательного согласования с владельцем, но он должен понимать публичность и использовать отдельную ветку для незаконченной работы. Отдельного DEV-каталога в текущем клиенте нет.

Общайся по-русски, понятными шагами для новичка. На запрос «как тут работать?» сначала дай карту проекта и простой реальный пример, а затем сопровождай изготовление и тестирование первого мода. Не проси у него пароли, ключи Unity, Supabase service-role или токены.

## Карта экосистемы

| Репозиторий / путь | Что хранит | Что править автору |
|---|---|---|
| `DnD-VTT-Content/packages/*.json` | Фактические небольшие игровые JSON-пакеты | Добавлять/версионировать мод |
| `DnD-VTT-Content/catalog/v3/index.json` | **Живой индекс пакетов**, читаемый Unity | Публиковать ID/URL/размер/SHA |
| `DnD-VTT-Content/catalog/v1/, v2/` | Исторические каталоги старых клиентов | Не менять без задачи на поддержку |
| `DnD-VTT-Content/schemas/catalog-entry-v1.schema.json` | Схема элемента **каталога** | Проверка формата, не шаблон полезной нагрузки |
| `DnD-VTT-Assets/packages/*.json` | Карты/примитивные модели/цвета | В другом репозитории |
| `DnD-VTT-Assets/catalog/v4/index.json` | Живой индекс ассетов/предпросмотров | Публикация графики |
| `DnD-VTT/experiment/unity-vtt/unity/Assets/Vtt/Runtime/WorkshopStore.cs` | Валидатор пакетов, безопасная установка | Только если меняется движок |
| `DnD-VTT/experiment/unity-vtt/unity/Assets/Vtt/Runtime/LegacySessionPanel.ContentManager.cs` | URL каталогов и UI мастерской | Только если меняется клиент |
| `DnD-VTT/experiment/unity-vtt/unity/Assets/Vtt/Runtime/WorkshopRuntime.cs` | Активация и загрузка ресурсов | Только если меняется движок |
| `DnD-VTT/experiment/unity-vtt/PROJECT_ATLAS.md` | Большой общий атлас исходников основного проекта | Искать, а не копировать целиком |

В этом репозитории два объекта: **payload** (`packages/<id>.json`) и **catalog entry** (элемент `packages[]` в `catalog/v3/index.json`). В payload должны совпадать `schemaVersion`, `id`, `version`, `type` с записью каталога. Каталог дополнительно задаёт `name`, `author`, `license`, `format`, `platform`, `unityVersion`, `dependencies`, `bytes`, `sha256` и `url`.

## Поддержка типов: не путать список категорий с исполнением

В текущем `WorkshopStore.ValidateData` активируются JSON: `race`, `class`, `feat`, `item`, `craft`, `map`, `model`, `environment`, `appearance`. Не все поля дают автоматические игровые эффекты. Категории `spell`, `subclass`, `monster`, `game-system`, `animation` и др. могут отображаться в UI, но **не имеют такого же пути активации через JSON**. Произвольные C#/JS/DLL/ZIP-моды не исполняются. Реальные 3D-модели, анимации и сложная логика требуют поддержки движка/доверенной сборки платформенных AssetBundle.

Характеристики и формат `seed` у рас/классов жёстко проверяются в C#. Пример `packages/dnd.class.blood_hunter.json` — лишь создание класса 1-го уровня: *не* полный движок класса на 20 уровней.

## Первый мод: собственная раса

Ниже учебный payload `packages/team.race.raccoonfolk.json`. Использовать только если имя/ID ещё свободны. Лицензию и авторство автор выбирает для **своей** оригинальной работы. Не копируй защищённый арт/тексты без разрешения.

```json
{
  "schemaVersion": 1,
  "id": "team.race.raccoonfolk",
  "version": "1.0.0",
  "type": "race",
  "races": [
    {
      "id": "team.race.raccoonfolk",
      "name": "Енотолюд",
      "desc": "Оригинальная тестовая раса команды.",
      "seed": {
        "stats": { "str": 10, "dex": 11, "con": 10, "int": 10, "wis": 10, "cha": 10 },
        "speed": "30 футов",
        "size": "Средний",
        "raceFeatureDescriptions": ["Ловкость +1."]
      },
      "choices": []
    }
  ]
}
```

Проверь исходный `demo.race.lanternfolk.json` для дополнительного контекста. Числа `stats` здесь соответствуют существующему формату начальных значений (в C# допустимы целые 8–12); **не заменяй их без разбора на +1/+2**. Ресурсный `id` должен принадлежать `id` пакета или повторять legacy-правило. Для класса нужны `seed`, `choices`, `hitDie` и `levelOneFeatures`. Для `item` обязательно поддерживаемое `inventoryCategory`. Для `model` в JSON доступны только перечисленные Unity-примитивы.

## Опубликовать новый JSON-мод без пересборки Unity

1. Убедись, что у тебя есть право записи в `DnD-VTT-Content`; для изменения существующего мода найди его **точный** файл через `docs/FILE_ATLAS.md`. Не создавай дубль ID.
2. Открой **отдельную рабочую ветку** GitHub (или форк) для незаконченного пакета. Создай/измени `packages/<id>.json`, сохрани валидный UTF-8 JSON; новая версия для ранее опубликованного ID должна быть больше прежней. Никогда не перезаписывай «как будто неизменный» старый релиз.
3. Возьми **точные байты** сохранённого файла, а не красиво отформатированный объект. Считай размер и SHA-256 после последнего изменения:

```bash
python3 -c "from pathlib import Path;import hashlib; p=Path('packages/team.race.raccoonfolk.json'); b=p.read_bytes(); print('bytes=',len(b)); print('sha256=',hashlib.sha256(b).hexdigest())"
```

   В PowerShell также допустим `(Get-Item packages/team.race.raccoonfolk.json).Length` и `(Get-FileHash packages/team.race.raccoonfolk.json -Algorithm SHA256).Hash.ToLower()`. Файл должен реально существовать на устройстве; вводить вымышленные контрольные суммы **запрещено**.

4. Добавь элемент в массив `packages[]` живого `catalog/v3/index.json`; сохрани другие элементы неизменными. URL формируется ровно так: `https://raw.githubusercontent.com/waitermisanthrope-creator/DnD-VTT-Content/main/packages/team.race.raccoonfolk.json`. Только URL доступного пакета на `main` поддерживается текущим клиентом. Перед публикацией проверь отсутствие дубликатов ID, зависимостей на отсутствующие пакеты, несовпадения версии, размера/хеша, формата и лицензии.
5. Пройди ревью/собственные проверки, затем отправь пакет **и** запись каталога в `main`; порядок при необходимости: сначала payload, затем индекс, чтобы каталог не ссылался на ещё отсутствующий файл. GitHub Pages и сборка APK не требуются.
6. Проверь **публичный raw-URL** пакета; скачай именно его и сверь SHA-256/байты с каталогом. Затем в Unity VTT → «Настройки» → «Мастерская дополнений» → «↻ Обновить каталоги» → найти ID → «Скачать и установить».
7. Для расы создай *нового* тестового персонажа и проверь имя, характеристики, сохранение/перезапуск. Установку на реальном устройстве отмечай только после реального теста.
8. Исправление = новый `version` + изменённый payload + новый `bytes`/`sha256` + обновление записи каталога. Для **уже публичного** пакета лучше сохранять следующую версию отдельным файлом (например, `packages/team.race.raccoonfolk-1.0.1.json`, но с **тем же** `id` внутри), чтобы старый опубликованный URL оставался доступен; в каталоге заменить `url` на новую версию. Клиент проверяет `id` внутри JSON, а не совпадение имени файла с ID. Не изменяй старые байты молча. Если не появился мод — сначала проверь кэш каталога, URL и сообщение валидатора. Если механика не работает — проверь, поддерживает ли Unity именно этот тип эффекта.

### Минимальный шаблон записи каталога

Значения в трёх полях ниже — **заглушки, не публиковать до точного расчёта**. `author` и `license` должны соответствовать реальному правообладателю и разрешению на распространение.

```json
{
  "schemaVersion": 1,
  "id": "team.race.raccoonfolk",
  "name": "Енотолюды",
  "version": "1.0.0",
  "author": "ИМЯ_РЕАЛЬНОГО_АВТОРА",
  "license": "ЛИЦЕНЗИЯ_С_РАЗРЕШЕНИЕМ_НА_РАСПРОСТРАНЕНИЕ",
  "type": "race",
  "format": "json",
  "platform": "any",
  "unityVersion": "*",
  "dependencies": [],
  "bytes": 0,
  "sha256": "ПЕРЕСЧИТАТЬ_ПО_ФАЙЛУ",
  "url": "https://raw.githubusercontent.com/waitermisanthrope-creator/DnD-VTT-Content/main/packages/team.race.raccoonfolk.json"
}
```

### Особенности публикации

- `main` каталог **публичен**. Рабочая ветка скрывает неопубликованный пакет от приложения; для теста именно через стандартную мастерскую нужно опубликовать в текущий публичный канал или заранее доработать клиент с DEV-каналом. Не обещай приватного тестирования внутри текущей мастерской.
- **Администраторы** команды, которым владелец дал GitHub write, вправе публиковать и править каталоги самостоятельно; внутренние бейджи Unity/Supabase не выдают GitHub-права автоматически.
- Не добавляй секреты, API-ключи, чужие личные сохранения, неразрешённые иллюстрации, исполняемый код или огромные бинарники. Держи совместимость Android/Windows и обратную совместимость ID/сохранений.
- Схема `schemas/package-manifest-v1.schema.json` описывает историческую/проектируемую структуру архива; **клиент её ZIP-пакеты не устанавливает**.
- В карточке Unity выводятся имя/автор/лицензия; одинаковые/поддельные author-строки не являются подтверждением авторства. Права на публикацию определяются GitHub и будущим сервером.
- Файлы каталога содержат версии и контрольные суммы; не применяй «безобидное форматирование» старого payload без обновления его hash.

## Если произошла ошибка — порядок диагностики для ИИ

1. Найди файл и тип через `docs/FILE_ATLAS.md`, сравни с работающим образцом.
2. Проверь парсинг JSON и нужные `id/version/type`, категорию и структуру `seed`/`items`/`races`/`classes`.
3. Проверь `catalog/v3/index.json`: уникальный ID, поля схемы, размер, SHA, доступный URL, имя, платформа, версия клиента.
4. Посмотри `WorkshopStore.ValidateManifest`, `ValidateData`, `Compatible` и `LegacySessionPanel.ContentManager` в Unity-ветке; никаких «магических» произвольных обработчиков.
5. Если пакет валидный и устанавливается, но эффект не исполняется — это **ограничение движка**, а не обязательно ошибка JSON. Зафиксируй блокер и предложи доработку Unity отдельно.
6. Дай владельцу/автору краткий отчёт: что изменено, пути и коммиты, что реально проверено, как воспроизвести, оставшиеся ограничения.
